# Demo: first interactive `loop_implement` run with shared Brain memory (2026-11-18)

Setup: `e3d` (Pi 1.5.0) started in a throwaway git repo, foreground `anthropic/claude-sonnet-5-5`, Brain connected through Pi's MCP, the E3D skill and extension loaded. The spec (`spec.md`) has two phases for a small TypeScript library, `addrkit`, and names no repository: it asks the writers to follow "the E3D SDK conventions in the shared memory notes". The writers were forced to `claude/haiku` and `codex/gpt-5.4-mini` with `MODEL_OVERRIDES`, so e3d-code's own routing did not choose them.

## The session

1. **Prompt:** *Use loop_implement on spec.md with action plan, and brain_paths ["kb/e3d-sdk.md"].*
2. **Plan (nothing run):** e3d-code's routing table plus the notes Brain would share.

   | Phase | Writer | Reviewer | Title |
   |---|---|---|---|
   | 1 | claude/haiku | openai | short addresses |
   | 2 | codex/gpt-5.4-mini | claude | address comparison |

   Brain would share one note: `note:01M4ZWJEEE9Q7SDPH0M3FST4HJ@e744d01c776bc1d4`.
3. **Auto or step:** the foreground model asked in chat. The first reply ("yes") did not answer the question, so it asked again; the next reply was "auto". It also asked whether to use a `check_command`; none was given.
4. **Run:** `loop_implement action=run mode=auto`. Both phases completed on a new `loop/task-…` branch in a worktree under `~/.local/state/e3d-loop/worktrees/`. Nothing was merged or pushed and the working tree was untouched.

| Phase | Writer | Files | Reviewer (different family) | Result |
|---|---|---|---|---|
| 1 short addresses | claude/haiku | `package.json`, `src/address.ts`, `test/address.test.ts`, `tsconfig.json` | openai/gpt-5.5 | 1 finding, not blocking |
| 2 address comparison | codex/gpt-5.4-mini | `src/address.ts`, `src/index.ts`, `test/address.test.ts` | anthropic/claude-sonnet-5-5 | 0 findings; the reviewer said it only read the files and ran nothing |

The memory packet was provided to both writers and both reviewers; the run record lists the same citation for each phase.

## What this run does and does not show

- **No check ran.** No `check_command` was given, so "passed" meant only that the writers finished and the reviews raised nothing blocking. The foreground model said so; Loop's own report did not. Fixed afterwards: a run without a check command now says "No check command was given: nothing was run to verify this code" in both the summary and the report (tested).
- **The phase 1 finding was not confirmed.** GPT-5.5 reported that the package metadata points consumers and TypeScript declarations at files that may not exist. The terminal output was truncated before the details, and nobody opened the full finding or the evidence file. Treat it as an unverified claim from the reviewer.
- **Memory use is unknown.** Loop records that the note was provided, not that any model used it. This run has no with-and-without comparison.
- **Auto versus step.** The model asked in chat and the user answered in chat. Whether Loop's own selection dialog appeared in the terminal was not recorded, so this run does not show that gate working in the interactive UI. Not verified.
- **No sandbox.** The writers ran unattended in a separate worktree, and could read the whole disk.
- **Pi update notice.** The startup banner offered Pi 1.5.2. Loop is pinned to 1.5.0 on purpose; upgrading is a deliberate step (see the README gotchas).

One run, small models, cheap spec: a demonstration that the flow works end to end interactively, not evidence that it improves results.
