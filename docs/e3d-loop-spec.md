E3D Loop — Interactive Multi-Model Engineering Spec v0.1 — November 8, 2026

E3D Loop
Interactive Multi-Model Engineering — Product and Technical Specification v0.1
FutCo LLC • November 8, 2026
Status: proposed implementation specification. This document authorizes no deployment, publishing, spending, or repository changes. Existing capabilities are distinguished from proposed adapters and new work. Initial product: a local interactive terminal coding environment for the maintainers, built on Pi.
# 1. Product thesis and outcome
E3D Loop is an interactive engineering partner that coordinates multiple models around real work. The user talks to one foreground agent, steers it naturally, inspects changes, interrupts execution, and resumes sessions. Behind that interface, bounded specialists can investigate, implement isolated subtasks, challenge assumptions, write tests, review changes, and propose creative alternatives.
The goal is better engineering outcomes: correctness, useful perspective, reasoning quality, creativity, speed, and controlled risk and cost. These goals can conflict. Additional models are justified only when their expected contribution exceeds the latency, coordination, privacy, and spend they introduce.
The first success criterion is that the maintainers voluntarily use E3D Loop for ordinary E3D development. The next is evidence that selective collaboration improves results relative to the same underlying model working alone. No claim of superior correctness or speed follows merely from having several models agree.
The product should feel familiar to a Claude Code user: launch in a repository, give a task, converse, watch tools execute, inspect diffs, and continue. It is not initially a new editor, remote company operator, or replacement for every existing E3D service.
# 2. Decisions and scope
D1. Pi compatibility is a product requirement: e3d-loop MUST support and expose all functionality of its pinned supported Pi release. It is Pi extended with E3D capabilities, not a reduced replacement or a second implementation of Pi. Preserve the upstream interactive experience, commands, CLI flags, models/providers, tools, sessions, branching, compaction, steering, interruption, configuration, skills, templates, themes, extensions/packages, MCP, and supported SDK/RPC integration surfaces. Maintain a compatibility inventory against the actual release; this list is illustrative, not a ceiling.
D1a. Reuse Pi through an E3D extension package and the thinnest necessary launcher. Existing Pi commands and configuration keep their meaning. Namespace added commands (for example /e3d-review) whenever names conflict. Existing Pi installations, sessions, packages, and workflows must remain usable without destructive migration or an E3D cloud account.
D1b. E3D extends this baseline with selective multi-model cooperation: independent investigation and review, complementary reasoning and perspectives, test design, bounded implementation delegation, creative alternatives, evidence-based reconciliation, and verified outcomes. Pilot supplies deliberation and existing pipeline capabilities; Brain supplies cited continuity; e3d-code, Corp, and Creative are reused through their supported interfaces. Better, faster, safer, and more correct work are measured objectives, not automatic consequences of adding models.
D1c. Full support does not mean every feature is enabled under every execution policy. Explicit user-selected profiles may restrict tools, extensions, network, or credentials. Show each restriction and its reason; never silently omit an upstream capability or label a restricted profile as unrestricted Pi parity. Never bypass isolation to preserve a feature: report an incompatibility and let the user choose an appropriate profile.
D1d. Pin upstream versions and retain notices. Test upgrades against the compatibility inventory before adopting them. Any unsupported upstream behavior is a documented release blocker for the corresponding parity claim, not silently removed scope. Maintain a fork only for a demonstrated limitation that cannot be resolved with supported interfaces or an upstream contribution.
D2. Start with macOS as the maintainers' daily environment; qualify Linux alongside it. Windows is a later compatibility target. Select the Node runtime from the intersection of the pinned Pi and E3D package requirements; current documentation points to Node 22.
D3. Keep one foreground conversational owner. Helpers return evidence and artifacts through the coordinator, not a noisy group chat.
D4. Reuse Pilot for deliberation, dissent, specialist councils, and its existing engineering pipeline. Reuse Brain for durable knowledge retrieval and proposals. Reuse e3d-code for phased CLI execution where appropriate. Reuse Corp for business authority and outcomes, and Creative for supported ideation.
D5. Ordinary interactive editing uses the Loop task lifecycle. A task explicitly delegated to the Pilot pipeline uses Pilot's lifecycle and gates. Never run both executors against the same workspace.
D6. Local operation and bring-your-own-model credentials must remain useful without an E3D account. Hosted Pilot services are optional additions.
D7. Core open-source license proposed: MIT, preserving upstream notices. Check exact pinned dependency licenses and provider terms before distribution; open-source code does not grant model-service redistribution rights.
MVP includes interactive coding, session resume, one selected execution model, one bounded independent helper, Pilot consultation, Brain retrieval and inbox proposals, durable task evidence, controlled tools, and verification. Parallel code writers, automated model routing, Corp dispatch, and generalized Creative engineering workflows follow later gates.
# 3. Ecosystem reuse and ownership
Pi — existing foundation: the complete interactive coding harness, model/provider support, tool loop, persistent sessions and branching, compaction, steering and interruption, SDK/RPC, skills, templates, themes, extensions, and built-in MCP client support. Reuse and expose these rather than building a parallel runtime. E3D work consists of collaboration behavior, ecosystem configuration/integration, bounded helper scheduling, evidence and verification, policy, and execution isolation.
Pilot — existing documented foundation: independent answers followed by critique, synthesis and dissent; provider adapters; expert lenses; local MCP pipeline tools; plan previews; worktrees; draft PR publication; hosted quotes and idempotency. New work: Loop adapter and capability checks. Any new cooperative-execution protocol belongs behind an explicit versioned interface, not assumed to exist today.
Brain — existing documented foundation: search/read/related, revision citations, capture into a review inbox, optional agent journals, report_use, and owner-run cognition proposals. New work: bounded context retrieval, session-to-evidence references, optional outcome capture. Brain remains advisory and never grants authority.
e3d-code — existing foundation: phased Markdown specs, provider/model overrides, fresh phase conversations, shared context, manifests, handoffs, resume, and independent verification. New work: a bounded subprocess adapter and mapping of its output into Loop task records. Do not silently inherit its unattended permission settings.
Corp — existing documented foundation: business events, correlation IDs, proposals, authority policies, Pilot handoff artifacts, and recorded outcomes. New work: importing an approved task reference and exporting evidence-backed status. Corp approval never grants arbitrary shell access.
Creative — existing foundation: structured briefs, contrasting directions, critique, artifact manifests, and evidence-grounded wildcard suggestions. Its wildcard command currently targets sales/marketing; it is not a general coding ideation API. Reuse as-is for supported tasks. General engineering alternatives require a new schema and tests, or use Pilot expert lenses first.
LiquidityWatch and e3d-lw-outlook — reference applications and evaluation tasks. Reuse the principle of model proposals followed by deterministic validation and later outcome checks. Do not import finance-specific scoring rules into code correctness.
Pilot Cloud — optional hosted councils. Reuse confirmed interfaces; exact integration contracts need implementation discovery. No new billing system is required for the local alpha.
Boundary: Pi owns model conversation state; Loop owns execution-task state and evidence; Pilot owns delegated engineering workflow state; Corp owns business authority; Brain stores cited interpretation. Adapters link IDs rather than duplicating another service's database.
# 4. Interactive experience
Proposed executable: e3d-loop [repository-path]. Proposed first-run setup discovers installed Pi/Pilot/Brain components, offers explicit configuration, checks provider availability, and shows the effective execution profile. It must not silently edit other clients' configuration.
The prompt remains available while helpers work. Status shows the active task, foreground provider/model, helper roles, workspace, execution profile, elapsed time, observed usage, reservations, and integration health. Long traces are collapsed; results explain what changed, what was checked, and what remains uncertain.
Proposed E3D additions include council, independent review, investigation, creative alternatives, Brain retrieval/capture, collaboration tasks, budget, and Pilot handoff. Reuse existing Pi commands for models, sessions, resume, cancellation, and other upstream functions wherever equivalent behavior already exists. The earlier command names are conceptual UX requirements, not a mandate to reimplement Pi. Preserve upstream commands and use names such as /e3d-council and /e3d-review for E3D additions when necessary. Natural-language access remains available.
Natural language must invoke the same operations: “Ask another model why this test fails,” “Have someone check the migration while you work on the API,” or “Stop the helpers and finish this yourself.” Slash commands are discoverable shortcuts, not a required programming language.
Interrupt semantics: a first interrupt stops new scheduling and requests cancellation of model calls and running tools. A force-stop terminates the managed process group and records possible partial effects. The UI distinguishes cancelled locally from a remote request that may still run or incur charges. It never claims that cancellation rolled back external actions.
Resumption shows the last verified snapshot, unfinished work, changed files, and uncertain external effects before continuing. Switching models retains task goals and evidence, with a rebuilt bounded handoff rather than assuming provider transcripts are interchangeable.
# 5. Collaboration patterns beyond debate
Foreground implementer: owns the active conversation and main patch. It can ask for help but cannot expand its own capabilities, spending ceilings, or data permissions.
Investigator: reads a snapshot and returns competing explanations, code references, reproductions, and suggested discriminating tests. It has no write access to the foreground tree.
Test designer: derives cases from requirements and invariants before seeing the implementer's rationale when practical. It can produce tests in an isolated workspace; the coordinator reviews the proposed test patch.
Reviewer: independently examines requirements, diff, and observed checks. It reports concrete defects, severity, locations, reproduction steps, and uncertainty. It cannot approve execution or declare a failing test acceptable by vote.
Specialist: provides security, performance, API, migration, UX, or domain perspective selected for the task. A role is not permanently assigned to a vendor; actual model identity and capability are recorded.
Alternative designer: proposes a bounded set of distinct approaches and cheapest experiments. Novelty alone is not selection evidence.
Pair assistance: foreground implementer asks one focused question; another model returns a short answer with evidence. This is the first collaboration mode.
Parallel investigation: two helpers inspect different hypotheses or code regions while the foreground agent continues unrelated safe work.
Independent review: a different provider/model reviews a fixed candidate snapshot. Findings are reconciled explicitly; each blocking finding is fixed, disproved with evidence, or accepted by the human as a documented exception.
Specialized implementation: later phase only. Workers edit separate worktrees, each with an assigned scope and acceptance criteria. The coordinator serializes integration and rechecks the combined result.
Bounded competition: later, opt-in. Two implementations of a difficult subproblem are compared against the same tests and operational constraints. Keep the winning artifact and the reason; discard losers without merging both.
Council escalation: use Pilot when independent results expose consequential disagreement or a difficult architectural choice. Pilot consensus is advisory; unresolved dissent remains visible.
# 6. Scheduling, routing, and cost control
Default alpha mode is assist: one foreground agent and at most one helper concurrently. Solo disables automatic helpers. Team later permits one foreground agent and up to two helpers by default, subject to CPU, context, provider, and spending limits.
Start with deterministic routing rules and user overrides. Select by tool capability, allowed data destination, context size, provider health, role fit, remaining budget, and measured outcomes. A cheap model that repeatedly needs repair is not automatically cheaper.
Suggested automatic triggers: a repeated failure without new evidence; a change to authentication, authorization, data migration, or public API compatibility; an ambiguous root cause; or an explicit user request for another perspective. Count repeated equivalent failures by error/signature and snapshot, not every tool exit.
Low-risk edits stay on the foreground model unless the user asks otherwise. A helper launch records its purpose, expected artifact, budget, timeout, snapshot, and why parallel work is useful. A second consultation requires new evidence or explicit escalation; no recursive “ask another agent” chains.
Model diversity is recorded, not inferred from display names. A second role using the same underlying model is labeled same-model review. Cross-provider diversity may help, but correlated errors remain possible.
All child work draws from one task budget. Reserve estimated cost before launching; limit maximum output and calls; reconcile actual usage when available. Missing usage is marked unknown and retains a conservative reservation. Never describe an estimate as a hard monetary guarantee where the provider cannot enforce it.
Hosted Pilot work uses its supported quote/idempotency contract. Foreground calls, helpers, councils, search, and retries all count toward the parent allowance. Reuse one idempotency key for a transport retry of the same request; use a new key for genuinely new work.
Default loop bounds: one initial independent review and one re-review after repairs; after two materially unchanged failures, pause and present evidence or ask for a focused investigation. Defaults are tunable policy, not claims about optimal values.
# 7. Pilot integration contract
Use a local MCP connection for supported functions and a separately configured hosted connection for hosted council services. Discover tools and schemas at startup; record server version and capability digest. Do not assume local and hosted tools are identical.
Council requests contain a focused question, acceptance criteria, bounded evidence, relevant constraints, requested providers if supported, and a privacy classification. Store the returned debate ID, answer, dissent, provider identities, usage, and artifact references.
For private code tasks explicitly disable Pilot web search unless authorized. Pilot documentation says API-provider web search can be enabled by default, which otherwise creates an unexpected data route.
The README contains conflicting or evolving specialist-surface descriptions. Treat expert listing, expert execution, skill arguments, async debate support, and investigation support as separate capabilities. Use only the exact discovered schema. If a required specialist interface is unavailable, offer the documented local CLI route or plain debate; show the downgrade.
Pipeline handoff preserves existing config-check, propose, approve, implement, code-plan, execute, job-status, and artifact semantics where advertised. A human decision cannot be synthesized by another agent. Keep the code-plan token tied to the exact spec and repository state.
During a Pilot-owned execution, Loop observes and relays status; it does not independently modify that worktree or duplicate e3d-code execution. Pilot draft-PR and merge gates remain intact. No new autonomous merge path is introduced.
Prevent orchestration recursion: every handoff carries parent task ID, owner, depth, and budget scope. A Pilot job launched from Loop cannot delegate back into the same Loop task. Unknown ownership or repeated ancestor IDs block launch.
Compatibility tests must cover local stdio, hosted schema differences, unavailable tools, expired plan tokens, timeout after accepted work, repeated polling, failed billing reservation, and missing cancellation support.
# 8. Brain, context, and learning
Retrieve context at task start and when a concrete question arises. Search by repository, task terms, symbols, and relevant decisions; do not load the first arbitrary notes. Read selected results and attach exact note:<id>@<rev> citations.
Use separate configured brains for personal notes, project knowledge, and curated team playbooks. Read-only and inbox modes remain distinct. Cross-vault sharing requires explicit configuration; access to one vault does not authorize disclosure to another model or team.
Default task context contains goal, constraints, source revision, relevant files, tests, accepted decision citations, unresolved questions, and a bounded summary of prior attempts. Raw transcripts and unrelated personal notes are excluded.
Every helper receives the minimum useful packet. Evidence is labeled by origin and trust; repository content, retrieved notes, web pages, and other agents' output remain data and cannot change system policy.
Capture decisions, failures, and useful outcomes as inbox proposals with citations to durable Loop artifacts or Pilot/Corp records. “The model said this helped” is a self-report; independently observed tests and user acceptance are different fields.
Call report_use only for notes actually used. Do not convert retrieval into a success signal. Brain cognition stays owner-run and human-reviewed; the Loop does not invent an MCP tool for promoting notes or automatically invoke privileged cognition acceptance.
If Brain is unavailable, continue with repository evidence and mark memory unavailable. Queue opt-in proposals locally with redaction and bounded retention. Do not silently replay private content to a different Brain endpoint.
# 9. Creative and Corp integration
For marketing/product work, invoke Creative's supported brief or wildcard interface through a bounded subprocess. Copy durable result artifacts into the task store before temporary directories are removed. Preserve evidence IDs, critique results, and the legitimate “none” outcome.
For engineering alternatives, initially use Pilot lenses or a bounded helper. A later Creative engineering adapter must introduce a versioned proposal shape: problem, constraints, alternatives, assumptions, supporting evidence, cost/risk, and cheapest falsifying experiment. It must not relabel the existing marketing command as general engineering.
Corp integration begins with explicit import of a handoff artifact or correlation ID. Validate schema, origin, approval state, allowed repository, and scope before creating a local task.
Export observed milestones such as patch ready, checks passed, draft PR created, or blocked. A created PR is not a shipped capability, and a shipped capability is not customer adoption or revenue.
Corp stays authoritative for business approvals. Loop stays authoritative for local execution receipts. Reconcile with stable correlation IDs and idempotent delivery, never by overwriting each other's histories.
# 10. Runtime architecture and package boundaries
Use a TypeScript/ESM workspace. Proposed packages: cli, core, pi-adapter, integrations/pilot, integrations/brain, integrations/code, integrations/corp, integrations/creative, policy, workspace, and evals. These are proposed repository paths, not existing modules.
The Pi adapter maps session events, interruption, model selection, extension tools, and persisted conversation references into a small Loop interface. Do not mutate Pi's internal message arrays as a substitute for its SessionManager; use supported session APIs.
The coordinator is deterministic application code around model proposals. It validates task transitions, budgets, ownership, artifacts, and tool permissions. A model may suggest a plan or helper; the coordinator decides whether it is permitted.
Use an internal event stream for UI updates and task persistence. Do not add a distributed queue, workflow service, or database server for the local alpha.
Use Pi's built-in MCP client for local stdio and remote Streamable HTTP connections, tool discovery, supported authentication, resources, and connection management. Configure Pilot and Brain through Pi rather than building a second MCP stack. In SDK-created sessions, explicitly load the built-in MCP extension and any required codemode/tool-search extensions. Add a thin E3D adapter only for domain contracts, capability validation, data policy, evidence, and error handling. Server process configuration remains trusted user configuration; repository content cannot authorize arbitrary server execution. MCP tool hooks support workflow policy but are not an OS isolation boundary.
Later remote workers implement the same task/artifact contract, with authentication, tenant isolation, and independent execution policy. Remote mode is a separate launch gate rather than exposing the local shell over HTTP.
# 11. Data contracts and durable state
TaskRequest fields: schemaVersion, taskId, sessionId, parentTaskId, origin, repositoryId, baseRevision, snapshotDigest, objective, acceptanceCriteria, constraints, allowedPaths, dataPolicy, executionProfile, budget, deadline, and correlationRefs.
Assignment fields: assignmentId, taskId, role, requestedProvider, actualProvider, modelId, contextDigest, snapshotDigest, read/write capabilities, expectedArtifact, maximumCalls, and cancellationToken.
WorkerResult fields: status (succeeded, failed, blocked, cancelled, unknown), evidenceRefs, proposedPatchRef, verificationRefs, findings, unresolvedQuestions, actualProvider/model, usage (observed/estimated/unknown), and timestamps. A successful model response is not equivalent to a successful engineering task.
Finding fields: findingId, severity, claim, sourceLocations, reproduction, evidenceRefs, snapshotDigest, resolution, and resolver. Resolution is fixed, disproved, human-accepted exception, or unresolved.
VerificationReceipt fields: checkId, trustedCommandRef, argv or command digest, cwd, environmentProfile, repository snapshot, exitCode, start/end time, output artifact/digest, and classification (passed, failed, pre-existing failure, not run, inconclusive).
Store state outside version-controlled source by default under a user-private E3D state directory keyed by canonical repo identity. Use SQLite transactions for coordinator state and an artifact directory for larger outputs; retain Pi session references rather than copying its storage model. Apply restrictive local permissions.
Task lifecycle: created → planned → running → verifying → awaiting_user or completed. blocked, failed, cancelled, and unknown are explicit states. Helper assignments have independent states; the parent cannot complete while required verification or blocking findings remain unresolved.
Commit task events and delivery outbox entries atomically. Events include sequence number, actor, parent linkage, model identity where applicable, evidence references, and timestamp. An exportable JSONL view supports inspection. Hashes detect content mismatch; they do not prove the recorded claim is true.
Schema migrations are versioned, backed up, and tested. Task/artifact exports remain portable. Retention and deletion are configurable; deleting local records cannot revoke content already sent to an external provider.
# 12. Workspace ownership and patch integration
Capture initial HEAD, dirty tracked changes, relevant untracked files, and user exclusions before editing. Never reset or stash the user's work automatically. A dirty workspace may be used interactively only with clear ownership boundaries.
There is exactly one writer per worktree. Read-only helpers inspect a frozen snapshot; write-capable helpers receive isolated worktrees or disposable copies. Git worktrees alone are not a security boundary.
Every patch declares its base snapshot, intended paths, and resulting digest. Reject stale bases, forbidden files, unexpected binary changes, and paths escaping the workspace. Stop for ambiguous user edits rather than overwriting them.
The coordinator integrates one candidate at a time, checks conflicts, runs targeted tests, then runs integration checks against the combined snapshot. Previously passing checks are invalidated by later relevant changes; a review applies only to its recorded snapshot.
A “read-only investigator” cannot run arbitrary repository code on the host. Tests, package scripts, and builds are executable code and must run under the same execution controls as implementation tools.
Cross-repository tasks are later scope: each repo has independent leases and checks; publication uses a manifest linking commits and PRs. No claim of atomic cross-repo rollback.
# 13. Permissions, isolation, and data protection
Pi's documented absence of a built-in permission system is a core design constraint. An extension hook alone must not be marketed as a security sandbox.
Support two clearly labeled profiles: local-trusted for the user's own reviewed code with explicit host execution authority; isolated for untrusted repositories and later hosted use. Local-trusted provides audit and workflow controls but cannot guarantee containment.
Isolated mode places execution workers and repository tools inside a configured container or VM boundary with restricted mounts, no host Docker socket, controlled network access, minimal environment, and ephemeral credentials. Provider credentials stay in a broker outside the code-execution environment where practical.
Verify every execution path: built-in shell, custom tools, direct shell shortcuts, extensions, MCP subprocesses, package scripts, and helper CLIs. If a path bypasses the policy broker, disable it in isolated mode or refuse startup. Never silently fall back to unrestricted host execution.
Policy actions include read, write, execute, network destination, secret access, git publication, merge, deployment, and destructive operations. Grants are scoped to task/session/path/action and cannot be expanded by model output, repository instructions, Brain notes, or council consensus.
Persist user authorization within its scope so routine work does not repeatedly prompt. Scope changes, newly sensitive destinations, or destructive actions require a new decision. OS enforcement and provider disclosure controls are separate from human approval UX.
Private-code defaults disable public gallery publication, telemetry content upload, and web-search forwarding. Per-provider allowlists determine where code and memory may go. Redaction is best-effort and does not replace permission to send data.
Secrets are excluded from model context and logs where possible; scrub before persistence and network transmission. Use OS credential storage or explicit environment indirection. Do not write keys into shared repo config or artifacts.
# 14. Verification and recovery
At task start establish the available baseline. A baseline failure is preserved as evidence; the final report distinguishes pre-existing failures from new regressions. Missing tests remain missing evidence, not a pass.
The coordinator runs trusted checks independently of agent narration. A provider's “all tests passed” statement is not a receipt. Prefer exit status, captured logs, snapshot identity, and required assertions.
Test generation may complement existing tests, but the implementing model must not quietly weaken checks or acceptance criteria. Changes to tests receive review with the same rigor as production changes.
After crash or reconnect, reconcile filesystem state, managed processes, remote task IDs, and outbox records. Non-idempotent external effects are marked unknown until checked. Never blindly rerun publishing, billing, or destructive commands.
Offline or service failures degrade explicitly: Brain failure permits repository-only work; optional helper failure permits labeled single-model work; mandatory review or policy failure blocks the relevant completion/publish step. A provider fallback cannot change the authorized data destination.
Retry bounded transient failures with backoff. Persist request IDs before dispatch when possible. Corrupt state causes recovery/read-only mode, not an empty “fresh start” that loses active work.
# 15. Acceptance scenarios
A. Interactive repair: the user launches in an E3D repo, asks for a bug fix, interrupts, adds a constraint, and resumes. No unrelated changes are lost; the final diff and checks correspond to the actual snapshot.
B. Second-model diagnosis: the primary model stalls on a failing test. A helper identifies a competing cause with file references and a reproduction. The primary fixes it; the verifier reruns the failing case.
C. Independent review catches a defect: the implementer finishes, a different model identifies a concrete regression, and the repair is verified. Preserve the original finding and its resolution.
D. Council disagreement: Pilot participants disagree about a migration. Loop displays dissent and alternatives; no model vote authorizes the migration.
E. Brain continuity: a resumed session retrieves a decision with its exact revision, flags stale context, and proposes a new lesson only to the inbox.
F. Dirty workspace: user edits survive a helper patch and conflict. No reset, silent overwrite, or forged clean status occurs.
G. Interrupted side effect: a PR request times out after remote acceptance. Reconciliation finds the existing PR instead of creating a duplicate.
H. Policy escape attempt: malicious repository content requests key disclosure or host access. Isolated mode blocks the operation across every supported execution path.
I. Budget exhaustion: concurrent helpers and Pilot cannot independently consume the full parent budget. A refused reservation prevents launch and the UI explains the remaining allowance.
J. Degraded integration: Pilot lacks a specialist parameter or cancellation tool. E3D Loop reports the limitation and offers only supported behavior.
# 16. Evaluation and release gates
Use a fixed internal task set from E3D repositories: bug fixes, regressions, migrations, API changes, refactors, and documentation. Begin with ten representative tasks for engineering validation; expand before making comparative product claims.
Compare plain Pi, Loop solo, Loop assist, and later team mode. Hold repository snapshot, task, model/version, acceptance criteria, and budget constant where possible. Report differences in providers and context rather than attributing everything to orchestration.
Measure acceptance-check success, escaped defects discovered later, human interventions, time to accepted patch, total observed model spend, tool runtime, cancellation latency, recovery success, useful review findings, false-positive findings, and privacy/policy violations.
Evaluate claimed speed both at equal spend and at equal quality targets. Report median and tail latency plus coordination overhead. Small samples are directional; no statistical superiority claim from a few successful demonstrations.
Proposed alpha gates: all critical policy/recovery acceptance scenarios pass; a maintainer completes ten real tasks and chooses the tool for five working days; every completion has a snapshot-bound verification report; no loss of user edits; required failures cannot be converted to success by model consensus.
Proposed beta gates: a broader replay set, measured collaboration benefit in at least one task category without unacceptable cost/latency regression, supported platform coverage, upgrade compatibility, and a security review before multi-user hosted execution.
# 17. Phase 1 — Pi foundation and interactive daily driver
Deliver a new e3d-loop repository containing an E3D Pi extension package, pinned dependency lock, compatibility inventory, example configuration, and only the launcher needed to expose the complete Pi experience. The first deliverable is usable Pi with Pilot and Brain connections and minimal E3D guidance. Reuse Pi's foreground model selection, streaming, interrupt, resume, and session persistence. Add minimal task/evidence references only where Pi does not already provide the required record.
Verify upstream functionality with a baseline Pi versus E3D-enabled compatibility suite: startup and CLI argument handling; native commands; provider/model selection; shell and file tools; session continue/resume/fork; compaction; steering and interruption; skills/templates/themes; third-party extension/package loading; MCP stdio/HTTP and authentication where configured; and the supported SDK/RPC paths. Include operation with E3D integrations disabled or unavailable. Inspect and test pinned release APIs instead of depending on undocumented internals.
Exit: the user can use the E3D-enabled installation for normal Pi workflows without losing upstream functionality, complete and resume a single-model task, and reach configured Pilot and Brain tools. The compatibility inventory records tested, untested, and policy-restricted capabilities; do not claim untested parity. Explicitly label local-trusted execution; isolated-profile claims wait for Phase 2.
# 18. Phase 2 — Policy, verification, and one cooperative helper
Implement the execution broker, isolated profile, capability discovery, task budget reservations, independent verification receipts, a single investigator/reviewer helper, and safe cancellation/recovery.
Keep helpers read-only at first. Add independent review with structured findings and bounded repair cycles. Store evidence before reporting completion.
Exit: acceptance scenarios A–C and F–I pass, including shell shortcuts and custom-tool escape checks. The alpha must not ship with an apparently safe mode that actually executes tools on the host.
# 19. Phase 3 — Pilot and Brain as first-class services
Implement local/hosted Pilot capability negotiation, focused council requests, explicit web-search policy, quote/idempotency support where available, and dissent display. Integrate Brain search/read/capture/report_use with bounded context and provenance.
Implement explicit Pilot pipeline handoff with ownership transfer, human gates, plan-token preservation, and artifact/status readback. Reuse e3d-code only through that owner or an explicitly separate bounded phase task.
Exit: scenarios D, E, and J pass; one real E3D task includes useful memory, an independent contribution, and a verified patch. Local operation works when hosted services are absent.
# 20. Phase 4 — Parallel execution and broader ecosystem loop
Add multiple helpers, isolated implementation worktrees, serialized patch integration, bounded creative alternatives, and model-switch handoffs. Add Corp import/outcome export and supported Creative commands.
Require stable file/branch ownership, cross-task budget accounting, durable artifacts, and integration-check invalidation before enabling parallel writers.
Exit: compare against assist mode on tasks with genuine parallelism. Disable unhelpful collaboration patterns by default. Do not add agents merely to populate a dashboard.
# 21. Initial backlog and ownership rules
Loop repository owns CLI experience, coordinator, adapter contracts, execution policy, task store, workspace integration, and evaluations.
Pilot changes belong in Pilot: missing specialist interfaces, versioned cooperative capabilities if needed, and any upstream pipeline behavior. Loop must not carry a private copy of Pilot's debate/convergence logic.
Brain changes belong in Brain: supported retrieval/citation/capture improvements. Loop must not bypass inbox review by editing the vault directly.
e3d-code changes belong in e3d-code: reusable phase-runner capability and manifest improvements. Loop integration should not duplicate its shell runner.
Creative changes belong in Creative only when engineering ideation has a defined reusable contract. Corp changes belong in Corp for new event types, authority rules, and handoff schemas.
Priority implementation tickets: Pi API compatibility spike; threat model and execution-path inventory; task/evidence schemas; foreground session adapter; workspace snapshot/ownership; verifier; helper protocol; Pilot adapter; Brain adapter; recovery/idempotency tests; daily-driver evaluation pack.
Dependencies: Phase 1 precedes Phase 2; Phase 3 uses Phase 2's policy/evidence primitives; parallel writers require Phase 4; hosted execution requires its own threat model and gates and is out of scope here. Build each phase with a small independently verifiable change set.
# 22. Open decisions and explicit exclusions
Confirm the exact Pi version and public API at implementation start. Confirm which provider/model combinations the maintainers want for foreground execution and independent review, including approved data destinations.
Choose the macOS isolation backend after testing actual file, process, and networking controls. Do not promise a particular backend before it works with required build tools.
Set per-task cost defaults using measured usage. Decide whether the initial branded command wraps Pi or installs an extension package based on the smallest supported implementation that preserves the interactive experience.
No initial custom foundation model, fine-tuning, model marketplace, new IDE, autonomous merging/deployment, general desktop automation, or mandatory cloud account. No automatic posting of work or private council content to public feeds.
Success is a dependable coding environment that selectively recruits useful help and can demonstrate the result. The durable advantage is the connection between decisions, execution, verification, and reviewed lessons—not the number of model calls.
